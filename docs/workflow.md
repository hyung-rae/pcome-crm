# 작업 및 문서 관리 절차

기획·완료 기준 확정 → 작업계획·테스트 시나리오 확정 → 개발 → 자동 테스트 → 브라우저 검증 → 코드 리뷰 → 문서 반영 → 사용자 확인 → 커밋 대상 최종 리뷰 → 커밋

## 1. 기획

사용자가 전달한 기능을 `planning/<기능-id>.md`에 초안으로 작성합니다.
목적, 범위, 사용자 흐름, 화면·동작, 데이터·권한, 예외와 완료 기준을 정리합니다.
완료 기준은 입력·조건·기대 결과를 명시해 테스트 가능한 형태로 작성합니다.
불명확한 사항은 미결 질문으로 남기고 대화하며 보완합니다. 임의로 확정하지 않습니다.
사용자가 기획을 확정하기 전에는 기능 개발을 시작하지 않습니다.

## 2. 작업계획

확정한 기획에 연결된 `plans/<기능-id>.md`를 작성합니다.
영향받는 코드·문서, 구현 순서, 의존 작업, 검증 방법을 정리합니다.
큰 기능은 사용자가 확인할 수 있는 작은 단위로 나눕니다. 개발 전에 완료 기준별 성공·실패 테스트 시나리오를 정합니다.
사용자가 작업계획과 테스트 시나리오를 확정한 후 개발을 시작합니다.

## 3. 개발

계획에 따라 개발하며 체크리스트와 진행 상태를 갱신합니다.
기획의 범위나 동작을 변경해야 한다면 사용자와 먼저 논의합니다.
변경의 영향과 추가 작업을 정리하여 사용자와 합의한 뒤 기획·계획에 반영하고 진행합니다.

## 4. 테스트 코드 및 브라우저 검증

- 작업계획에 기획 완료 기준별 자동 테스트와 브라우저 검증 시나리오를 포함합니다.
- 기능 개발 후 해당 기능의 테스트 코드를 작성하고 실행합니다. 핵심 동작, 입력 검증, 예외와 회귀 위험을 검증하며 구현을 그대로 반복하는 테스트는 피합니다.
- 기능에 맞는 단위·통합·E2E 테스트를 선택합니다. 테스트 도구가 없다면 작업계획에 도입 내용을 포함합니다.
- 린트·타입 검사·빌드와 관련 테스트를 실행합니다.
- 로컬 서버를 실행하고 실제 브라우저에서 주요 사용자 흐름과 예외 동작을 직접 확인합니다. 화면 변경은 레이아웃과 관련 화면 크기도 확인합니다.
- 브라우저의 콘솔 오류와 실패한 네트워크 요청도 확인합니다.
- 실패하면 원인을 수정하고 관련 테스트와 브라우저 시나리오를 다시 실행합니다.
- 작업계획에 실행 명령, 테스트 파일, 결과, 브라우저·URL·시나리오, 발견한 문제와 재검증 결과를 기록합니다.
- 실행할 수 없거나 확인하지 못한 항목은 이유와 남은 검증을 명시합니다. 실제로 확인하지 않은 결과를 통과로 기록하지 않습니다.

## 5. 코드 리뷰

요구사항 누락, 불필요한 복잡도, 권한 및 데이터 처리, 기존 기능에 미치는 영향을 점검합니다.
발견한 문제를 수정하고 영향을 받는 테스트·브라우저 시나리오를 재검증합니다.
리뷰 결과와 남은 사항을 작업계획에 기록합니다.

## 6. 문서 반영

- 기획의 완료 기준과 계획의 검증 항목을 확인하고 결과를 기록합니다.
- `features/<기능-id>.md`에 실제 동작, 경로, 데이터, 정책, 예외, 코드 위치와 제한을 기록합니다.
- 공통 구조나 데이터 변경은 `architecture/`의 해당 문서에 반영합니다.
- 중요한 선택과 이유는 `decisions/`에 남깁니다. 모든 작은 수정에 결정 기록을 만들지는 않습니다.
- `docs/README.md`의 기능 목록과 `overview.md`의 현재 상태를 갱신합니다.
- 실행 방법이 바뀌면 루트 README도 갱신합니다.
- 미구현·미검증 사항을 명시하고, 충족하지 못한 완료 기준을 완료로 표시하지 않습니다.

## 7. 사용자 확인 및 커밋

검증·리뷰·문서 반영이 끝나면 상태를 `사용자 확인 대기`로 두고 변경 내용, 검증 결과, 제한을 전달합니다.
에이전트의 검증 완료와 사용자의 최종 확인을 구분합니다.
사용자 최종 확인 후 커밋할 실제 변경분을 다시 리뷰합니다.

- `git status`, 변경 diff 및 커밋에 포함할 파일을 확인합니다. 새 파일은 내용도 확인합니다.
- 요구사항 누락, 버그·회귀, 권한·데이터 처리, 테스트 누락, 문서와 구현 불일치를 점검합니다.
- 의도하지 않은 파일, 비밀정보 및 무관한 변경이 포함되지 않았는지 확인합니다.
- 문제를 발견하면 수정하고 필요한 검증과 리뷰를 다시 수행합니다. 사용자 확인 이후 동작·범위가 바뀌면 다시 확인받습니다.
- 리뷰 결과를 작업계획에 기록합니다. 별도 계획이 없는 작은 수정은 완료 보고에 기록합니다.
- 해결되지 않은 중대한 문제가 있으면 커밋하지 않고 사용자에게 알립니다.

최종 리뷰까지 마치면 완료로 표시하고, 합의한 Git 이모지 규칙으로 목적별 커밋을 만듭니다. 커밋 내용이 리뷰한 변경분과 일치하는지 확인합니다.
최종 확인 전에는 커밋하지 않습니다. 사용자가 별도로 지정한 커밋 지시는 우선합니다.
배포가 필요한 작업은 배포 방법·권한·배포 후 확인 항목을 별도로 합의합니다.

## 문서 유지 규칙

- 기능 ID는 `customer-search`처럼 짧은 영문 kebab-case로 정하고 세 디렉토리에서 동일하게 사용합니다.
- 각 문서에 상태·최종 갱신일·연관 문서 링크를 남깁니다.
- 날짜는 한국 시간 기준 `YYYY-MM-DD`로 기록합니다.
- 기획 상태는 `초안 → 논의 중 → 확정`, 계획 상태는 `작성 중 → 확정 → 진행 중 → 사용자 확인 대기 → 완료`로 관리합니다.
- 기능 문서는 현재 구현을 기준으로 유지하며, 후속 변경도 같은 문서에 반영합니다.
- 완료된 기획·계획은 삭제하지 않고 이력으로 유지합니다. 후속 작업은 별도 작업 ID로 연결합니다.
- 요구사항의 의도는 기획, 구현 순서·검증 이력은 계획, 현재 동작은 기능 문서에 기록해 중복을 줄입니다.
- 작은 수정은 기존 기능 문서와 관련 계획을 갱신합니다. 별도 기획·계획은 새 기능이나 사용자 흐름·정책이 달라지는 작업에 작성합니다.
- 문서에 비밀 키, 토큰, 개인정보를 기록하지 않습니다.
