# 작업 및 문서 관리 절차

기획·완료 기준 확정 → 작업계획·테스트 시나리오 확정 → 개발 → 자동 테스트 → 브라우저 검증 → 코드 리뷰 → 문서 반영 → 사용자 확인 → 커밋 대상 최종 리뷰 → 커밋

## 절차 선택

파일 수보다 변경이 동작에 미치는 영향으로 판단합니다.

| 절차 | 대상 | 시작 방식 |
|---|---|---|
| 기본 | 새 기능, 사용자 흐름·업무 정책·권한·데이터 구조 변경 | 기획 확정 → 작업계획 확정 → 개발 |
| 간소 | 오타, 일부 UI·UX 조정, 원인이 명확하고 영향이 제한된 버그, 기존 기능의 작은 보완 | 요청·수정 범위 요약 → 개발 |

간소 절차는 수정 범위를 짧게 설명하고 “작은 수정으로 보고 간소 절차로 진행하겠습니다”라고 알린 뒤 진행합니다.
사용자 요청을 해당 범위의 승인으로 보며 별도 기획·계획 문서 작성과 확정 단계를 생략합니다.
기존 기능의 수정도 사용자 흐름·정책이 바뀌면 기본 절차를 적용합니다. 접근 권한이나 결제 계산 변경은 코드가 작아도 기본 절차 대상입니다.
작업 중 영향이 커지거나 새로운 정책 결정이 필요하면 구현을 멈추고 기본 절차로 전환하여 사용자와 합의합니다.

간소 절차에서도 아래 테스트·브라우저 검증·리뷰·문서 반영·사용자 최종 확인·커밋 규칙은 유지하며, 검증·리뷰·문서의 범위는 4단계의 `간소 절차 기준`을 따릅니다.
그 기준보다 줄이는 테스트·리뷰 생략은 별도 사용자 승인이 필요합니다. 기능 문서가 없으면 관련 구조·절차 문서와 완료 보고에 기록합니다.
없는 기획·계획을 기록만을 위해 새로 만들지는 않습니다.

아래 1~2단계의 기획·계획 확정은 기본 절차에 적용합니다.

## 1. 기획

사용자가 전달한 기능을 `planning/<기능-id>.md`에 초안으로 작성합니다.
목적, 범위, 사용자 흐름, 화면·동작, 데이터·권한, 예외와 완료 기준을 정리합니다.
완료 기준은 입력·조건·기대 결과를 명시해 테스트 가능한 형태로 작성합니다.
불명확한 사항은 미결 질문으로 남기고 대화하며 보완합니다. 임의로 확정하지 않습니다.
사용자가 기획을 확정하기 전에는 기능 개발을 시작하지 않습니다.

## 2. 작업계획

확정한 기획에 연결된 `plans/<기능-id>.md`를 작성합니다.
영향받는 코드·문서, 구현 순서, 의존 작업, 검증 방법을 정리합니다.
큰 기능은 사용자가 확인할 수 있는 작은 단위로 나눕니다. 개발 전에 완료 기준별 성공·실패 테스트 시나리오를 정합니다.
테스트 도구 도입이 필요하면 개발 전 작업계획에 포함합니다.
문서 상단에 상태와 3~5줄의 현재 요약을 두고, 진행·검증·리뷰 이력은 아래 섹션에 추가합니다.
사용자가 작업계획과 테스트 시나리오를 확정한 후 개발을 시작합니다.

## 3. 개발

계획에 따라 개발하며 체크리스트와 진행 상태를 갱신합니다.
기획의 범위나 동작을 변경해야 한다면 사용자와 먼저 논의합니다.
변경의 영향과 추가 작업을 정리하여 사용자와 합의한 뒤 기획·계획에 반영하고 진행합니다.

## 4. 변경 영향에 따른 검증

아래 범위는 사용자가 승인한 기본 기준입니다. 이 범위 선택은 매번 생략 승인을 묻지 않습니다.
기준보다 검증을 줄이거나 리뷰 자체를 생략할 때는 별도 승인을 받습니다.

| 변경 유형 | 기본 검증 |
|---|---|
| 문서·오타만 변경 | diff 리뷰, 공백 검사, 변경된 로컬 링크 확인. 앱 테스트·빌드·브라우저는 대상 아님 |
| 일부 UI·스타일 | 관련 테스트·변경 화면 시각 확인·변경 파일 린트. 타입 영향 시 타입 검사, 번들·설정 영향 시 빌드 |
| 기능·로직 | 관련 단위·통합 테스트와 연결된 사용자 흐름, 관련 린트·타입 검사. 서버·번들·라우팅 영향 시 빌드 |
| 인증·권한·공통 구조·의존성 | 영향받는 기능의 폭넓은 회귀 테스트, 린트·타입 검사·빌드, 주요 브라우저 흐름 |

- 시작 시 변경 영향과 검증 범위를 작업계획 또는 간소 절차 안내에 기록합니다.
- 핵심 동작·입력·예외·회귀를 확인하는 기존 테스트를 활용하고 필요한 테스트만 추가합니다. 구현을 반복하는 테스트를 늘리지 않습니다.
- 순수 함수 테스트는 원격 계정·환경 파일·개발 서버 없이 실행하고 외부 연결은 통합·E2E로 검증합니다.
- 자동 E2E는 동작, 별도 브라우저 시각 검토는 변경 화면의 배치·가독성을 확인합니다. 같은 흐름을 여러 도구로 반복하지 않습니다.
- 반응형 영향이 있는 화면 크기만 확인합니다. 브라우저 검증에서 예상치 못한 콘솔·네트워크 오류도 확인합니다.
- 성공 결과는 관련 코드·테스트·설정·의존성·환경이 유지되면 재사용합니다. 다른 작업 변경이 유입되면 영향받는 결과의 유효성을 다시 판단합니다.
- 실패나 변경 뒤에는 해당 항목과 영향받는 회귀만 재실행합니다. 영향이 불명확하거나 공통 기반이 바뀌면 범위를 넓힙니다.
- 성공 로그는 짧은 요약만 확인하고 전체 로그는 필요 시 로컬 파일에 저장합니다. 실패한 항목의 필요한 부분만 읽으며 비밀정보를 노출하지 않습니다.
- 실행 중에는 적절한 대기 간격을 두고 변화 없는 상태를 반복 조회하지 않습니다.
- 정한 검증 통과와 리뷰 지적 해결 후 종료합니다. 새 위험·변경·실패 없이 검증을 늘리지 않습니다.
- 명령·범위·결과·미검증 제한을 기록하며 미실행을 통과로 표시하지 않습니다.

### 간소 절차 기준

사용자가 2026-10-22 합의한 간소 절차의 검증·리뷰·문서 범위입니다. 접근 권한·결제 계산·데이터 처리에 영향이 있으면 적용하지 않고 기본 기준을 따릅니다.
간소 절차에서는 위 변경 유형별 기본 검증의 수행 시점·범위보다 이 기준이 우선합니다.

| 항목 | 기준 |
|---|---|
| 연속 조정 | 사용자가 브라우저로 보며 같은 화면을 이어서 조정하는 동안에는 변경 파일 린트만 수행하고, E2E·에이전트 시각 확인은 사용자 확인으로 대신합니다. 이벤트 처리·폼 제출·API 호출처럼 동작이 바뀌는 조정만 해당 흐름의 E2E spec을 즉시 1회 실행합니다. |
| 커밋 전 일괄 검증 | 사용자가 확인 완료나 커밋을 지시하면 조정한 화면의 관련 E2E spec·단위 테스트, 정적 검사, 빌드(해당 시), 시각 확인, 커밋 직전 리뷰, 문서 반영을 1회 수행합니다. 실패하면 해당 항목만 고쳐 재실행합니다. |
| 시각 확인 | 일괄 검증 때 화면 크기 1개를 기본으로 하고 레이아웃·반응형 동작이 바뀔 때만 영향받는 화면 크기를 추가합니다. 위치·크기는 Playwright 수치 검증(boundingBox 등)을 우선하고 스크린샷은 화면당 변경 영역 1장만 봅니다. |
| 리뷰 | 개발 후에는 diff 자기 점검만 하고, 정식 리뷰는 7단계 커밋 직전 리뷰 1회로 수행합니다. |
| 문서 | 기능 문서만 갱신합니다. 관련 작업계획이 있으면 한 줄만 추가하고, `docs/README.md`·`overview.md`는 기능 상태가 바뀔 때만 갱신합니다. |

E2E는 실제 Supabase·개발 서버가 필요하고 오래 걸리므로 git hook으로 강제하지 않고 위 일괄 검증 단계에서 실행합니다.

### 테스트·리뷰 생략 제안

위 표에서 해당 변경에 필요한 검증과 리뷰(기본 절차는 개발 후 리뷰·커밋 직전 리뷰, 간소 절차는 커밋 직전 리뷰)는 기본 절차입니다.
변경 범위와 위험을 검토해 일부 절차를 생략해도 된다고 판단하면 사용자에게 생략 여부를 먼저 묻습니다.

- 생략할 정확한 항목, 이유, 남는 위험과 대신 수행할 확인을 간결하게 설명합니다.
- 사용자가 명시적으로 승인한 항목만 해당 작업에서 생략합니다. 답변이 없으면 승인으로 간주하지 않습니다.
- 이미 같은 작업·범위에 대해 승인받았다면 다시 묻지 않습니다. 변경 범위가 커지면 재평가합니다.
- 승인받지 못하면 기본 절차를 수행합니다. 실행 불가는 생략 승인과 구분하여 보고합니다.
- 생략한 항목은 통과로 표시하지 않고 `사용자 승인으로 생략`으로 기록하며, 사유와 승인 내용을 작업계획 또는 완료 보고에 남깁니다.
- 이 예외 규칙은 기획·계획 확정, 사용자 최종 확인 및 커밋 권한을 대신하지 않습니다.

## 5. 코드 리뷰

요구사항 누락, 불필요한 복잡도, 권한 및 데이터 처리, 기존 기능에 미치는 영향을 점검합니다.
발견한 문제를 수정하고 영향을 받는 테스트·브라우저 시나리오를 재검증합니다.
리뷰 결과와 남은 사항을 작업계획에 기록합니다.
간소 절차는 개발 후 diff 자기 점검으로 대신하고 정식 리뷰는 7단계 커밋 직전 리뷰에서 1회 수행합니다.

## 6. 문서 반영

간소 절차는 4단계 `간소 절차 기준`의 문서 범위를 따릅니다. 아래는 기본 절차 기준입니다.

- 기획의 완료 기준과 계획의 검증 항목을 확인하고 결과를 기록합니다.
- `features/<기능-id>.md`에 실제 동작, 경로, 데이터, 정책, 예외, 코드 위치와 제한을 기록합니다.
- 공통 구조나 데이터 변경은 `architecture/`의 해당 문서에 반영합니다.
- 중요한 선택과 이유는 `decisions/`에 남깁니다. 모든 작은 수정에 결정 기록을 만들지는 않습니다.
- `docs/README.md`의 기능 목록과 `overview.md`의 현재 상태를 갱신합니다. `overview.md`에는 작업 이력을 쌓지 않고 현재 구현·검증 요약·제한만 고쳐 씁니다.
- 실행 방법이 바뀌면 루트 README도 갱신합니다.
- 미구현·미검증 사항을 명시하고, 충족하지 못한 완료 기준을 완료로 표시하지 않습니다.

## 7. 사용자 확인 및 커밋

검증·리뷰·문서 반영이 끝나면 상태를 `사용자 확인 대기`로 두고 변경 내용, 검증 결과, 제한을 전달합니다.
에이전트의 검증 완료와 사용자의 최종 확인을 구분합니다.
사용자 최종 확인 후 대상 파일과 개발 후 리뷰 이후의 변경분을 확인합니다. 이전 리뷰가 유효하면 전체 재리뷰를 반복하지 않습니다. 이전 리뷰가 없거나 범위를 추적할 수 없으면 전체 대상을 리뷰합니다. 간소 절차는 개발 후 정식 리뷰가 없으므로 전체 diff를 리뷰합니다.

- `git status`, 변경 diff 및 커밋에 포함할 파일을 확인합니다. 새 파일은 내용도 확인합니다.
- 요구사항 누락, 버그·회귀, 권한·데이터 처리, 테스트 누락, 문서와 구현 불일치를 점검합니다.
- 의도하지 않은 파일, 비밀정보 및 무관한 변경이 포함되지 않았는지 확인합니다.
- 문제를 발견하면 수정하고 필요한 검증과 리뷰를 다시 수행합니다. 사용자 확인 이후 동작·범위가 바뀌면 다시 확인받습니다.
- 리뷰 결과를 작업계획에 기록합니다. 별도 계획이 없는 작은 수정은 완료 보고에 기록합니다.
- 해결되지 않은 중대한 문제가 있으면 커밋하지 않고 사용자에게 알립니다.

최종 리뷰를 마치거나 해당 리뷰의 생략을 사용자에게 승인받으면 완료로 표시하고, 합의한 Git 이모지 규칙으로 목적별 커밋을 만듭니다. 커밋 내용이 리뷰한 변경분과 일치하는지 확인합니다.
최종 확인 전에는 커밋하지 않습니다. 사용자가 별도로 지정한 커밋 지시는 우선합니다.
배포가 필요한 작업은 배포 방법·권한·배포 후 확인 항목을 별도로 합의합니다.

## 문서 유지 규칙

- 기능 ID는 `customer-search`처럼 짧은 영문 kebab-case로 정하고 세 디렉토리에서 동일하게 사용합니다.
- 현재 상태·최신 검증 요약을 먼저 읽고 상세 이력은 필요한 구간만 읽습니다. 여러 문서에 긴 이력을 중복하지 않습니다.
- 각 문서에 상태·최종 갱신일·연관 문서 링크를 남깁니다.
- 날짜는 한국 시간 기준 `YYYY-MM-DD`로 기록합니다.
- 기획 상태는 `초안 → 논의 중 → 확정`, 계획 상태는 `작성 중 → 확정 → 진행 중 → 사용자 확인 대기 → 완료`로 관리합니다.
- 기능 문서는 현재 구현을 기준으로 유지하며, 후속 변경도 같은 문서에 반영합니다.
- 완료된 기획·계획은 삭제하지 않고 이력으로 유지합니다. 후속 작업은 별도 작업 ID로 연결합니다.
- 요구사항의 의도는 기획, 구현 순서·검증 이력은 계획, 현재 동작은 기능 문서에 기록해 중복을 줄입니다.
- 작은 수정은 기능 문서를 갱신하고 관련 계획에는 한 줄만 추가합니다. 별도 기획·계획은 새 기능이나 사용자 흐름·정책이 달라지는 작업에 작성합니다.
- 문서에 비밀 키, 토큰, 개인정보를 기록하지 않습니다.
